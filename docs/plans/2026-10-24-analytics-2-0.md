# Analytics 2.0 – „Tableau für Ingo“

**Date:** 2026-10-24 · **Status:** phases 1–3 deployed 2026-10-24 (engine v2.0.0, web app, write path, agent prompt/skills); Streamlit replaced · replaces the Streamlit app (`vogelring-analytics`, analytics.vogelring.com)

## Goal

A visual analytics workspace for ornithologists (Ingo) that needs no SQL and no data-science knowledge, with
exactly the functions this domain needs, and a LibreChat agent that can do everything the user can do in the app:
explore data, build views, assemble workbooks, write reports and presentations, and create reusable
"Auswertungen" (pipelines) that then appear as one-click cards for the user.

Decisions (2026-10-24, Anton): Vue 3 + Vuetify (same look as vogelring.com) · live read-only Postgres role
(never a write path into vogelring) · one container on the Pi serving web app + MCP + downloads at
analytics.vogelring.com · embedded LibreChat drawer inside the app · everything German.

## Product model (Tableau simplified)

| Tableau | Analytics 2.0 (German UI) | Spec |
|---|---|---|
| Data source | **Datenquelle** – curated: Sichtungen, Beringungen, Vögel (1 Zeile je Ring), Beziehungen, plus gespeicherte Datensätze | `SourceSpec` (server-defined) |
| Filter shelf | **Filter** – Art, Ort/Ortsgruppe ({{Definition}}), Zeitraum, Monate/Jahreszeit, Jahre, Ring(e), Status, Alter, Melder, Umkreis um Ort | `FilterSpec` → SQL WHERE (parameterised) |
| Worksheet (shelves) | **Ansicht** – „Was zählen?“ (Sichtungen · Vögel · Beobachtungstage · Summe/Mittel von Spalte), „Aufteilen nach“ (x), „Farbe nach“ (Serie), „Kacheln nach“ (Facetten); Typ: Diagramm / Karte / Tabelle | `ViewSpec` → dataset + Chart/Map/TableSpec (existing engine) |
| Dashboard | **Mappe** – Raster gespeicherter Ansichten mit gemeinsamen Filtern | `WorkbookSpec` |
| Story | **Bericht** (PDF/DOCX) und **Präsentation** (PPTX) aus Mappe oder Ansichten | `ReportSpec` (exists), `DeckSpec` |
| Prep flow | **Auswertung** – gespeicherte, parametrisierte Rezepte (vom Agenten oder aus der Mappe gespeichert), als Karte mit Formular | `PipelineSpec` |
| – | **Begriffe** – Definitionen (Ortsgruppen, Zeiträume, Vogelgruppen) | exists (`definitions.py`) |
| – | **Notizen/Projekte** – Langzeitgedächtnis des Agenten je Projekt | `notes` (catalog) |

Everything is a JSON spec in shared stores. The web app and the MCP tools are two clients of the same engine, so
whatever the agent builds shows up in the app and vice versa.

**Live mirror (Anton, 2026-10-24):** Ingo can keep the chat on one screen and the analytics app on the other and
watch the agent work without refreshing. The engine has an in-process event bus; every store change (dataset,
visual, view, workbook, pipeline run, report, deck, note) is published on an SSE stream (`/api/events`). The web app
subscribes: lists update in place, and the **Live** page always shows the agent's newest artefact as it appears
(plus a running log in plain German: „Karte erstellt: …“). The agent can also *steer* the app: a tool
`show_in_app(target)` publishes a navigation event so the analytics screen jumps to the view/workbook the agent is
talking about.

## Architecture

```
analytics/                      (repo folder; was analytics-mcp/)
  agent/                        prompt/ and skills/ for the LibreChat agent
  deploy/, Dockerfile           Pi deployment (one container)
  server/  (Python 3.12, uv)    vogelring_analytics package
    events.py                   event bus + SSE (/api/events), show_in_app navigation events
    sources.py                  curated sources + FilterSpec → SQL (params), German labels/choices
    views.py                    ViewSpec → (dataset via sources/transforms) → Chart/Map/TableSpec → model
    workbooks.py                WorkbookSpec (tiles, shared filters), render all tiles
    pipelines.py                PipelineSpec (parameters + steps), run → artifacts
    decks.py                    DeckSpec → PPTX (python-pptx, house template)
    catalog.py                  SQLite catalog: views, workbooks, pipelines, runs, notes (+ owner, tags, search)
    api.py                      REST for the web app (/api/…), identity from Cf-Access-Authenticated-User-Email
    server.py                   MCP tools (existing + views/workbooks/pipelines/decks/notes/sources)
    app.py                      Starlette: /api, /mcp, /viz, /reports, /files, /tiles, static web app (SPA fallback)
    … existing: db, datasets, definitions, transforms, analysis, charts, maps, tables, reports, render/
  web/     (Vue 3, Vuetify 3, TS, Vite)
    Start · Erkunden (Builder mit Live-Vorschau) · Mappen · Auswertungen · Berichte & Präsentationen ·
    Begriffe · Daten (Tabelle/Export) · Agent-Drawer (LibreChat iframe) · Einstellungen
  Dockerfile                    stage 1: node build web → stage 2: playwright-python image, serves web/dist
  deploy/pi-deploy.sh           rsync → build → up (replaces streamlit container :8501)
```

Rendering: the engine builds renderer-agnostic models (as today). The browser renders them live with the same
`chart.js`/`map.js` (moved into the Vue app as components) – no server round-trip for interaction; the server
renders PNG/PDF/PPTX for exports via headless Chromium (as today).

Safety: one DB role `librechat_reader` (SELECT only), read-only transactions, statement timeout, SQL guard; the
engine has no write-capable connection. Analytics data lives in `/data` (parquet, SQLite). No materialized views in
the vogelring database.

## Gated write path (Anton, 2026-10-24)

Ingo needs data migrations the app cannot do in bulk (e.g. ring „W408“ is a Farbring: 65 sightings must move to the
colour-ring fields). Rules: strongly gated, rollbackable, dry run first, fully transparent, final write approved by
the user in LibreChat (tool approval card). Design:

- Separate Postgres role `vogelring_agent_writer` (UPDATE on whitelisted columns of sightings/ringings, INSERT/UPDATE
  on color_rings, no DELETE, no DDL) and a separate lazily opened pool (`WRITE_DATABASE_URL`); all analytics stays on
  the read-only role.
- Typed operations only (set_fields, rename_place, convert_to_color_ring, upsert_color_ring, merge_reading_to_ring),
  never free SQL. `propose_changes` = dry run → changeset (`chg_…`, status proposed) with every affected row's
  before/after values, German summary (counts per operation and field, examples, warnings) and a preview page
  `/changes/{id}`. `apply_changes` = one transaction, rows locked, before-values re-verified, rowcounts asserted,
  after-values recorded → status applied. `rollback_changes` restores the recorded before-values (inserted registry
  rows are reported as a manual step since the role cannot delete).
- LibreChat `endpoints.agents.toolApproval`: allow `mcp:vogelring-analytics:*`, ask for `apply_changes` and
  `rollback_changes` (configured on the Pi). The agent prompt/skill `aenderung-vorschlagen` enforces: clarify →
  propose → explain in plain German → apply only after an explicit yes → report → note.

## 2026-10-24 – Gruppen-Logik: Oder/Ausschluss, Vogelebene, Verknüpfen

Anlass (Beispiel von Anton für die Art von Fragen, die Ingo stellt – die konkrete Regel ist erfunden): „Zeig mir alle Orte,
an denen die Vögel auftauchen, die im Ostpark mausern“ – wobei „Mauser im Ostpark“ etwa heißen könnte: im Ostpark in
Mai/Juni gesehen **oder** im April mit Status MG. Welche Regel gilt, sagt immer der Nutzer. Das war mit reinem Und-Filter nicht ausdrückbar und
brauchte außerdem die Vogelebene (erst Vögel bestimmen, dann alle ihre Sichtungen).

- **Filtersprache** (`sources.py`): `FilterFields` (Und-Verknüpfung aller Felder; `groups` = in mindestens einer Gruppe,
  neu `all_groups` = in allen, `exclude_groups` = ohne) → `FilterBlock` (+ `any_of` = mindestens eine Teilbedingung,
  `none_of` = keine; Teilbedingungen sind `FilterFields`, also bewusst **eine** Ebene, damit das JSON-Schema nicht rekursiv
  wird – LibreChats zod-Konvertierung und die Modelle kommen damit zurecht) → `FilterSpec` (+ `birds_of` / `birds_not_of`:
  `FilterBlock` auf Vogelebene, kompiliert zu `ring IN (SELECT DISTINCT ring FROM v_sightings … WHERE …)`, bei Beziehungen
  über beide Ringe). Tiefere Verschachtelung geht über Gruppen (Gruppen-Tiefe ≤ 3, Bedingungs-Tiefe ≤ 4).
  `describe_filters` erklärt alles auf Deutsch: „… entweder (in den Monaten Mai–Juni) oder (im April, mit Status
  Mausergast), aber nicht (…), von Vögeln mit mindestens einer Sichtung …“.
- **Gruppen** (`groups.py`): `scope` = `sightings` (nur passende Sichtungen) oder `birds` (Vogelgruppe: alle Sichtungen
  der Vögel mit mindestens einer passenden Sichtung). `group_summary` liefert für Vogelgruppen zusätzlich
  `matching_sightings`; die Vorschau markiert je Zeile `matches` (erfüllt die Bedingung selbst vs. weitere Sichtung
  desselben Vogels). `engine.combine_groups(name, union|intersection|difference, ids, scope)` legt eine referenzierende
  Gruppe an (folgt späteren Änderungen der Ausgangsgruppen); REST `POST /api/groups/combine`.
- **Agent**: keine neuen Tools (create_group/create_view nehmen die Felder im Schema mit); `filter_choices.filters` ist jetzt
  ein freies JSON (Schema −15 KB). Prompt und Skill `gruppe-anlegen` erklären Oder/Ausschluss, Vogelebene, Verknüpfen und
  das proaktive Angebot, Auswahlen als Gruppe zu speichern. Der Prompt liegt in Mongo (`agents.instructions`) und muss
  nach dem Rsync per mongosh eingespielt werden.
- **Web**: FilterPanel mit Oder-/Ausschluss-Blöcken und „Vögel statt Sichtungen“, Gruppenart-Umschalter und
  Bedingungsmarkierung auf der Gruppenseite, Dialog „Verknüpfen“, „Als Gruppe speichern“ in Erkunden.
- Nebenbefunde: Leaflet-Zoom per Mausrad/Trackpad war viel zu empfindlich (`wheelPxPerZoomLevel` 60 → 240, `zoomSnap`
  0.5); und das Root-`.gitignore` (Python-Vorlage: `lib/`, `data`, `*.sql`) hatte `web/src/lib/`,
  `vogelring_analytics/data/ring_species.json` und `server/sql/` aus dem Commit 986f679 herausgehalten – ein frischer
  Klon hätte nicht gebaut. `analytics/.gitignore` nimmt sie jetzt wieder auf.
